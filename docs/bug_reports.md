## BUG-001 UTF-16 の CSV が「ヘッダー不正」になり、「文字コード非対応」と報告されない

| 項目 | 内容 |
|---|---|
| 発見日 | 2026-10-23 |
| 発見工程 / テスト | 工程3 / UT-SVC-13b(`ImportService` に UTF-16 のバイト列を渡すケース) |
| 対象 | `app/domain/csv_rules.py` の `decode()`(CSV-02) |
| 関連要件 | REQ-018、NFR-002 |

### 現象

UTF-16 で保存した CSV(Excel の「Unicode テキスト」など)を取り込むと、400 `CSV_HEADER_INVALID`(ヘッダー行が正しくない)が返る。
設計(CSV-02)では、UTF-16 は 400 `CSV_ENCODING_UNSUPPORTED`(文字コード非対応)となるはずだった。

### 再現手順

```python
from app.domain.csv_rules import decode
decode("date,amount,category\n".encode("utf-16"))     # → ("shift_jis", "d\x00a\x00…")
decode("date,amount,category\n".encode("utf-16-le"))  # → ("utf-8", "d\x00a\x00t\x00…")
```

### 期待結果

`None` を返す(API では 400 `CSV_ENCODING_UNSUPPORTED`)。

### 原因

- UTF-16 では、ASCII 文字が「文字コードの1バイト + `0x00`」の2バイトになる。この並びは UTF-8 としても有効なバイト列なので、BOM のない UTF-16LE / BE は UTF-8 として「デコードに成功」してしまう。
- BOM 付きの UTF-16(`FF FE`)は UTF-8 では失敗するが、cp932 では `FF` / `FE` がユーザー定義領域の文字として読めてしまい、Shift_JIS として成功する。
- 設計では「UTF-8 → cp932 の順に試してデコードできるか」で判定しており、UTF-16 がこの両方をすり抜ける場合を考慮していなかった。

**設計の考慮漏れ**として分類する。単体テストの仕様を作る段階で、異常系の同値クラス「UTF-16」に ASCII だけのヘッダーを使ったケースを加えたことで発見した。

### 修正内容

- `decode()` の先頭に、次の判定を追加した。
  - UTF-16 / 32 の BOM(`FF FE` / `FE FF`)で始まる → 対応外
  - NUL バイト(`0x00`)を含む → 対応外
- 正当な UTF-8 / Shift_JIS のテキストに NUL バイトは現れないため、正常なファイルには影響しない。
- 設計書 06_csv_import_design.md の CSV-02 の疑似コードに、同じ判定を追記した。

### 影響範囲

CSVインポート(API-24)の文字コード判定だけ。保存データへの影響はない(修正前もヘッダーエラーで中断しており、1行も取り込まれていなかった)。
